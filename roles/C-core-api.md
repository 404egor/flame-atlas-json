# Роль C — Core і API: ранжування, покриття, прогалини, експорт

**Кому підійде:** тому, хто любить чисті функції, тести й числа; бекенд-розробнику чи аналітику.
**Місія:** написати логіку, яка робить продукт корисним для науковця: чесне пояснюване ранжування,
карту покриття, список прогалин, порівняння й експорт.

## Зона відповідальності

- `packages/core/` — чисті функції без мережі й LLM, з тестами.
- `apps/web/app/api/` — усі маршрути, крім `ask` і `explain`.
- `data/processed/scenarios.json` — файл (зміст дає E).

**Готово, коли:** три контрольні сценарії дають очікуваний верх списку; експорт відкривається в Excel;

### Якщо лишився час
- Проста модель межі: логістична регресія «займання / не займання» від O₂ на таблиці CFI-G
  (колонки `XO2`, `Hot ignition`, `Cool flame?`). Тільки після підтвердження E, що колонки означають саме це.
  Показувати з довірчим інтервалом і підписом «ілюстративна модель на даних одного дослідження».

## З ким синхронізуватись

- **D**, щодня кілька разів: форми даних для екранів, особливо Compare і Coverage.
- **A**, на старті й о 18:30: яких полів `TestRecord` бракує.
- **E**: контрольні сценарії і перевірка прогалин.

## Ризики ролі

- Багато `null` у тиску й потоці. Ранжування не має карати дослідження за відсутність даних сильніше,
  ніж за невідповідність: тому невідоме дорівнює 0.5 плюс застереження.
- Рядки рівня «день тестів» і «матриця умов» мають діапазони й переліки. Сітка покриття рахує такий
  рядок у кожній клітинці, куди потрапляють його значення, і це треба підписати в інтерфейсі.
- Спокуса віддати ранжування LLM. Не робимо: бал рахує код.

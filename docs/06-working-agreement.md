# Як ми працюємо з AI-агентами

## 1. Рішення

**Не беремо цілком ні BMAD, ні Spec Kit. Працюємо за спрощеною схемою «контракти спершу»:**
один спільний файл контексту для всіх агентів, заморожені контракти даних, список задач
на кожну команду з критеріями готовності, власники папок, перевірка після кожного кроку.

З обох методів беремо ідеї, а не інструменти. Причина проста: у нас 34 години й п'ятеро людей,
які працюють паралельно. Обидва методи розраховані на інший режим.

## 2. Що показало дослідження (14 листопада 2026)

| Підхід | Що це | Чому не підходить як процес для всієї команди |
|---|---|---|
| **BMAD, повний цикл** | агенти-ролі (аналітик, PM, архітектор, scrum master, розробник, QA); перед кодом створюються Product Brief, PRD, Architecture, епіки й історії | багато документів до першого рядка коду; історії виконуються по одній; на освоєння п'ятьма людьми підуть години |
| **BMAD Quick Flow** | окремий короткий шлях: замість PRD і архітектури одна технічна специфікація, далі реалізація й рев'ю | добре для однієї людини з однією задачею; нічого не каже про узгодження п'яти паралельних потоків |
| **GitHub Spec Kit** | команди constitution → specify → clarify → plan → tasks → implement на кожну функцію | команди виконуються послідовно одним розробником і одним агентом; паралельна робота спирається на зовнішні засоби git, а не на сам інструмент |
| **OpenSpec** | легкі пропозиції змін до специфікації | найшвидший старт, але сильний у доопрацюванні наявного коду, а в нас порожній репозиторій |

Що кажуть джерела:

- Документація BMAD описує Quick Flow як паралельний шлях для малих зрозумілих задач, який пропускає
  фази планування, а повний метод рекомендує командам від двох розробників
  ([Quick Flow](https://docs.bmad-method.org/explanation/quick-flow),
  [Workflow Map](https://docs.bmad-method.org/reference/workflow-map/)).
- Навчальний модуль Microsoft про Spec Kit для команд наголошує на спільних версіонованих артефактах,
  ранньому обміні специфікаціями й розподілі роботи через список задач
  ([Microsoft Learn](https://learn.microsoft.com/en-us/training/modules/spec-driven-development-github-spec-kit-enterprise-developers/10-scale-spec-driven-development-team-collaboration)).
  Саме це ми й робимо, тільки без інструмента.
- Порівняння 2026 року радять для хакатону чи прототипу легші засоби (OpenSpec або Spec Kit), а BMAD —
  для великих проєктів. Одне з них оцінює старт так: OpenSpec близько 5 хвилин, Spec Kit близько 30 хвилин,
  BMAD від годин до днів
  ([dev.to](https://dev.to/willtorber/spec-kit-vs-bmad-vs-openspec-choosing-an-sdd-framework-in-2026-d3j),
  [developertoolkit.ai](https://developertoolkit.ai/en/ecosystem/frameworks/spec-driven-frameworks/)).
  Це оцінки авторів блогів, а не виміри.
- ThoughtWorks тримає Spec Kit у кільці Assess, тобто «варто вивчати»
  ([Technology Radar](https://www.thoughtworks.com/es/radar/languages-and-frameworks/github-spec-kit)).

Висновок: жоден з інструментів не розв'язує нашу головну задачу — щоб п'ять агентів у п'яти людей
писали сумісний код одночасно. Її розв'язують спільний контекст, контракти й власники папок.

## 3. Що беремо з кожного підходу

| Ідея | Звідки | Де вона в нас |
|---|---|---|
| Незмінні принципи проєкту | Spec Kit, constitution | `AGENTS.md`, розділ 2 |
| Специфікація → план → задачі з критеріями готовності | Spec Kit | `docs/01-product-spec.md` → `docs/02-architecture.md` → `tracks/*.md` |
| Самодостатня історія з усім контекстом для агента | BMAD | задача в `tracks/*.md` з кроками й критерієм готовності |
| Агенти-ролі | BMAD | дві команди з трьома іменними відповідальностями |
| Одна коротка специфікація замість пакета документів | BMAD Quick Flow | кожен документ — одна сторінка |
| Спільні версіоновані артефакти в git | Spec Kit для команд | усе в репозиторії, зміни через коміти |

## 4. Правила

1. **Один контекст для всіх.** Кожна сесія агента починається з `AGENTS.md` і списку задач своєї команди.
   `AGENTS.md` читають Claude Code, Cursor, Codex, Copilot та інші; для Claude Code є `CLAUDE.md` з імпортом.
2. **Контракти спершу.** Типи з `docs/04-contracts.md` і фікстури існують з першої години.
   Ніхто не чекає на чужий код: усі працюють проти фікстур.
3. **Власник папки.** У чужій папці не правимо. Потрібна зміна — пишемо власнику.
4. **Зміна контракту — через чат.** Абзац «що міняю і навіщо» → власник контрактів погоджує → правка → рядок у журналі рішень.
5. **Спершу план, потім код** для задач довших за 30 хвилин. План агента читає людина.
6. **Малі кроки.** Гілка `<команда>/<номер-задачі>` живе недовго. `main` завжди збирається.
7. **Рішення записуємо.** Один рядок у `docs/decisions.md`: що вирішили, чому, хто.
8. **Людина відповідає за результат агента.** Перед злиттям читаємо diff. Маппінги таблиць і промпти
   читаємо особливо уважно.
9. **Агент не є джерелом фактів про горіння.** Факти беруться з документів PSI з посиланням.
10. **Журнал AI.** Кожен коротко пише в `docs/si-usage-log.md`, що робив з AI: це обов'язкове поле подання.

Склад команд, блокери й порядок кроків: [09-groups-and-blockers.md](09-groups-and-blockers.md)
і [05-timeline.md](05-timeline.md).
